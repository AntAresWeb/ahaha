# Архитектура проекта "Ahaha"

## 1. Введение
Ahaha — это автоматизированная система для поиска, анализа и отклика на вакансии с платформы HeadHunter. Система построена как набор микросервисов, взаимодействующих через асинхронную очередь сообщений. Основная цель — минимизировать ручной труд соискателя, сохраняя при этом высокое качество и персонализацию откликов.

## 2. Общие архитектурные принципы
- **Микросервисная архитектура**: Каждый сервис решает одну задачу и может быть развернут независимо.
- **DDD (Domain-Driven Design)**: Моделирование предметной области находится в центре разработки.
- **Асинхронное взаимодействие**: Сервисы общаются через RabbitMQ, что обеспечивает слабую связанность.
- **Чистая архитектура (Hexagonal)**: Бизнес-логика изолирована от внешних адаптеров (БД, API, очереди).

## 4. Описание микросервисов

| Сервис | Назначение | Ключевые обязанности |
|--------|------------|----------------------|
| **Gateway** | Веб-интерфейс и API-шлюз | - Отображение дашборда<br>- Управление настройками<br>- Ручной запуск задач<br>- Отдача статики |
| **Fetcher** | Получение вакансий | - Запрос к HH API по расписанию<br>- Первичная фильтрация<br>- Сохранение новых вакансий в БД<br>- Публикация задач на анализ |
| **Analyzer** | LLM-обработка | - Загрузка полного текста вакансии<br>- Оценка соответствия резюме<br>- Генерация текста отклика<br>- Принятие решения о готовности к отправке |
| **Sender** | Отправка откликов | - Проверка лимитов отправки<br>- Отправка через HH API<br>- Отслеживание статуса<br>- Логирование результатов |

## 5. Связи и потоки данных

### Поток 1: Получение вакансий
1. **Триггер:** Расписание (каждые N минут) или команда из Gateway.
2. **Fetcher** → делает запрос к HH API (с фильтрами по профессии).
3. **Fetcher** → сохраняет вакансии в БД (таблица `vacancies`).
4. **Fetcher** → для каждой новой вакансии создает запись в таблице `analysis` со статусом `pending`.
5. **Fetcher** → публикует сообщение в очередь `analyzer.pending` с `vacancy_id` и `resume_id`.

### Поток 2: Анализ вакансий
1. **Analyzer** → забирает сообщение из очереди `analyzer.pending`.
2. **Analyzer** → загружает полный текст вакансии из HH API.
3. **Analyzer** → отправляет запрос к Ollama (промпт + резюме + вакансия).
4. **Analyzer** → получает результат (оценка соответствия и текст отклика).
5. **Analyzer** → обновляет запись в `analysis` (статус `analyzed`/`rejected`, `match_score`).
6. Если `match_score` > порога → **Analyzer** публикует сообщение в очередь `sender.ready`.

### Поток 3: Отправка откликов
1. **Sender** → забирает сообщение из очереди `sender.ready`.
2. **Sender** → проверяет лимиты (суточные, интервальные).
3. **Sender** → отправляет отклик в HH API.
4. **Sender** → сохраняет результат в таблице `responses`.
5. **Sender** → обновляет статус в `analysis` на `sent`.

## 6. Инфраструктура

| Компонент | Назначение |
|-----------|------------|
| **PostgreSQL** | Основное хранилище данных (вакансии, резюме, анализы, отклики) |
| **RabbitMQ** | Брокер сообщений (асинхронное взаимодействие) |
| **Ollama** | Локальный LLM-сервер для анализа и генерации текста |
| **Docker** | Контейнеризация всех сервисов |
| **Nginx** | (Опционально) Обратный прокси для Gateway |

## 7. Безопасность и управление доступом
- Все внешние API (HH) используют OAuth2-токены, хранящиеся в `.env`.
- Внутренние сервисы общаются через изолированную Docker-сеть.
- Ведется журнал всех действий для аудита.

## 8. Развертывание
- `docker-compose up -d` — поднимает всю инфраструктуру и сервисы.
- Каждый сервис собирается в отдельный образ.
- Используются переменные окружения для гибкой настройки.

## 9. Мониторинг и логирование
- Структурированные логи в формате JSON.
- Healthcheck-эндпоинты для каждого сервиса (`/health`).
- Базовые метрики в Prometheus (планируется).
